
1. 트랜잭션 격리 수준과 이상 현상

트랜잭션이 동시에 실행될 때 발생할 수 있는 이상 현상들을 이해하고, 이를 해결하기 위한 격리 수준의 개념을 알아본다.



1.1. 트랜잭션 동시 실행 시 발생하는 이상 현상
여러 트랜잭션이 동시에 실행될 때, 데이터의 일관성이 깨지는 다양한 이상 현상이 발생할 수 있다.



더티 리드 (Dirty Read) 

커밋되지 않은(아직 확정되지 않은) 데이터를 읽는 현상이다.

예시: 트랜잭션 1이 x 값을 10에서 80으로 변경했지만 커밋하지 않은 상태에서, 트랜잭션 2가 이 변경된 80을 읽고 처리한다. 이후 트랜잭션 1이 롤백되면, 트랜잭션 2가 읽었던 80은 유효하지 않은 데이터가 된다. 

반복 불가능한 읽기 (Non-Repeatable Read) 

하나의 트랜잭션 안에서 같은 데이터를 두 번 읽었는데, 그 값이 달라지는 현상이다.

예시: 트랜잭션 1이 x 값을 두 번 읽는데, 첫 번째 읽을 때는 10을 읽고, 그 사이에 트랜잭션 2가 x 값을 50으로 변경하고 커밋하면, 두 번째 읽을 때는 50을 읽게 된다. 

팬텀 리드 (Phantom Read) 

동일한 조건으로 데이터를 조회했을 때, 조회되는 행의 개수가 달라지는 현상이다.

예시: 트랜잭션 1이 v=10인 데이터를 읽는데, 처음에는 하나의 튜플만 읽는다. 그 사이에 트랜잭션 2가 v=10인 새로운 튜플을 추가하고 커밋하면, 트랜잭션 1이 다시 v=10인 데이터를 읽을 때 두 개의 튜플을 읽게 된다. 



1.2. 이상 현상 해결을 위한 격리 수준 (Isolation Level)
이상 현상들을 모두 막으려면 데이터베이스 성능이 저하될 수 있어, 일부 이상 현상을 허용하는 격리 수준을 통해 성능과 일관성 사이의 균형을 맞춘다.



격리 수준의 필요성 

이상 현상들은 데이터 불일치를 발생시켜 좋지 않다.

모든 이상 현상을 막으면 동시 처리 가능한 트랜잭션 수가 줄어 DB 성능이 저하된다.

따라서 일부 이상 현상을 허용하는 격리 수준을 선택하여 사용한다.

격리 수준의 종류 (SQL 표준 기준) 

Read Uncommitted: 세 가지 이상 현상(더티 리드, 반복 불가능한 읽기, 팬텀 리드) 모두 허용. 동시성이 가장 높지만 이상 현상에 가장 취약하다.

Read Committed: 커밋된 데이터만 읽으므로 더티 리드를 허용하지 않는다. 반복 불가능한 읽기와 팬텀 리드는 허용한다.

Repeatable Read: Read Committed가 허용하지 않는 것을 허용하지 않으면서, 반복 불가능한 읽기까지 허용하지 않는다. 팬텀 리드는 허용한다.

Serializable: 세 가지 이상 현상을 모두 허용하지 않는다. 이상 현상 자체가 발생하지 않는 가장 엄격한 레벨이다.



1.3. 표준 격리 수준의 한계와 추가 이상 현상
1992년 SQL 표준에서 정의된 격리 수준 외에도 다양한 이상 현상이 존재하며, 이를 해결하기 위한 논의가 있었다.



표준 격리 수준 비판 (1995년 논문) 

이상 현상 정의가 모호하다.

3가지 외에도 더 많은 이상 현상이 존재한다.

상업적 DBMS의 실제 사용 방식을 반영하지 않았다.

추가 이상 현상

더티 라이트 (Dirty Write) 

커밋되지 않은 데이터를 덮어쓰는 현상이다.

예시: 트랜잭션 1이 x를 10으로 변경 후, 트랜잭션 2가 x를 100으로 변경한다. 이후 트랜잭션 1이 롤백되면, 트랜잭션 2의 변경 내용이 사라지거나 데이터가 꼬일 수 있다. 

로스트 업데이트 (Lost Update) 

한 트랜잭션의 업데이트가 다른 트랜잭션에 의해 덮어쓰여 사라지는 현상이다.

예시: x=50에서 트랜잭션 1이 51을 더해 101로 만들고, 트랜잭션 2가 150을 더해 201로 만든다. 만약 트랜잭션 1이 50+51=101을 계산하고, 트랜잭션 2가 50+150=200을 계산하여 x에 쓴 후, 트랜잭션 1이 101을 쓰면 트랜잭션 2의 200이라는 업데이트가 사라진다. 

더티 리드의 확장된 개념 

롤백되지 않아도 더티 리드가 발생할 수 있다.

예시: 트랜잭션 1이 x에서 40을 빼서 x를 60으로 변경한다. 이때 트랜잭션 2가 x=60, y=50을 읽고 합계 110을 계산한다. 이후 트랜잭션 1이 y에 40을 더해 y를 90으로 변경한다. 최종적으로 x=60, y=90이 되지만, 트랜잭션 2가 읽은 시점(x=60, y=50)과 최종 결과(x=60, y=90)가 달라 데이터 불일치가 발생한다. 

리드 스큐 (Read Skew) 

서로 관련 있는 데이터를 읽을 때, 한 트랜잭션 내에서 데이터가 불일치하게 읽히는 현상이다.

예시: x=50, y=50에서 트랜잭션 1이 x에서 80을 인출하려 하고, 트랜잭션 2가 y에서 90을 인출하려 한다. 둘 다 x+y=100이므로 인출 가능하다고 판단하지만, 트랜잭션 1이 x를 -31로 변경하고, 트랜잭션 2가 y를 -41로 변경하면, 전체 합이 0보다 커야 한다는 제약 조건을 위반하게 된다. 

현상 스큐 (Write Skew) 

서로 다른 데이터에 쓰기를 하더라도 결과적으로 데이터 불일치가 발생하는 현상이다.

예시: x=10, y=10에서, 트랜잭션 1은 x+y를 x에 쓰고, 트랜잭션 2는 x+y를 y에 쓴다. 만약 트랜잭션 1이 x=10, y=10을 읽고 x에 20을 쓰고, 트랜잭션 2가 y=10을 읽고 y에 20을 쓰면 최종 결과는 x=20, y=20이 된다. 하지만 정상적인 경우라면 x=30, y=30 또는 x=20, y=30 등이 되어야 한다. 



1.4. 스냅샷 격리 (Snapshot Isolation)
스냅샷 격리는 특정 시점의 데이터 복사본(스냅샷)을 기준으로 트랜잭션을 처리하여 일관성을 유지하는 방식이다.



스냅샷 격리의 개념 

기존 표준 격리 수준과 달리, 동시성 제어 구현 방식에 기반한다.

트랜잭션 시작 시점의 데이터 스냅샷을 기준으로 동작한다.

개념적 이해를 위해 예제를 통해 설명한다.

스냅샷 격리의 동작 방식 

트랜잭션은 시작 시점의 데이터 스냅샷을 읽는다. 

데이터 변경은 해당 트랜잭션의 스냅샷에만 반영된다. 

커밋 시점에 스냅샷의 변경 내용이 실제 데이터베이스에 적용된다. 

쓰기-쓰기 충돌 (Write-Write Conflict) 발생 시, 먼저 커밋된 트랜잭션만 인정하고 후속 트랜잭션은 롤백 처리한다. 

스냅샷 격리의 특징 

MVCC (Multi-Version Concurrency Control)의 한 종류이다.

트랜잭션 시작 시점 기준으로 커밋된 데이터만 보인다. 

먼저 커밋한 트랜잭션이 승리하는 'First Committer Wins' 방식을 따른다. 



2. 실제 RDBMS의 격리 수준 구현
주요 RDBMS들은 SQL 표준을 기반으로 격리 수준을 제공하지만, 구현 방식과 제공하는 레벨에 차이가 있다.



2.1. MySQL의 격리 수준
InnoDB 엔진 사용 시, 표준 SQL의 4가지 격리 수준(Read Uncommitted, Read Committed, Repeatable Read, Serializable)을 제공한다.

문서에서는 이 세 가지 이상 현상을 중심으로 격리 수준을 설명한다.



2.2. Oracle DB의 격리 수준
표준 SQL 격리 수준을 기준으로 설명하지만, Read Uncommitted 레벨은 제공하지 않는다.

Repeatable Read와 Serializable 레벨 사용 시, Serializable로 지정하도록 권장한다.

주로 사용되는 격리 수준은 Read Committed와 Serializable이다.

Oracle의 Serializable 격리 수준은 스냅샷 격리 수준으로 동작한다.



2.3. SQL Server의 격리 수준
세 가지 이상 현상을 기준으로 5가지 격리 수준을 정의한다.

스냅샷 격리 수준을 제공하며, 이는 앞서 설명한 스냅샷 격리와 유사하게 동작한다.

표준 SQL 격리 수준을 기반으로 설명한다.



2.4. PostgreSQL의 격리 수준
표준 SQL의 4가지 격리 수준을 동일하게 제공한다.

표준 3가지 현상 외에 추가적인 이상 현상도 함께 고려하여 레벨을 구분한다.

PostgreSQL의 Repeatable Read 레벨은 스냅샷 격리 수준으로 동작한다.



2.5. 개발자를 위한 격리 수준 활용 방안
사용하는 DBMS의 격리 수준 특성을 잘 파악하고 적절하게 선택해야 한다.

기본값으로 사용해도 큰 문제는 없지만, 성능 튜닝이나 이상 현상 발생 시 대비를 위해 각 레벨의 동작 방식을 이해하는 것이 중요하다.

표준 3가지 현상 외 다양한 이상 현상을 아는 것이 문제 해결에 도움이 된다.



3. 락을 이용한 동시성 제어
락(Lock)은 트랜잭션 간의 동시 접근을 제어하여 데이터 일관성을 유지하는 기본적인 방법이다.



3.1. 락의 기본 개념과 종류
락의 필요성 

동시에 같은 데이터에 대한 읽기/쓰기가 발생하면 예상치 못한 결과가 발생할 수 있다.

락은 이러한 문제를 해결하기 위해 사용된다.

락의 동작 방식 

데이터마다 락이 존재하며, 변경하거나 읽으려면 락을 취득해야 한다.

락을 취득하지 못하면 획득할 때까지 기다려야 한다.

락의 종류

라이트 락 (Write Lock, Exclusive Lock) 

쓰기 목적뿐만 아니라 읽기에도 사용될 수 있다.

획득 시 다른 트랜잭션의 동시 읽기 및 쓰기를 허용하지 않는다.

리드 락 (Read Lock, Shared Lock) 

읽기 목적으로 사용된다.

다른 트랜잭션의 동시 읽기를 허용한다.

쓰기 요청이 들어오면 데이터를 보호하기 위해 블록한다.

락 호환성 

리드 락과 리드 락은 서로 호환된다.

라이트 락과 리드 락, 라이트 락과 라이트 락은 서로 호환되지 않아 블록이 발생한다.



3.2. 2단계 락킹 프로토콜 (2PL)
2PL은 트랜잭션의 시리얼라이저빌리티(Serializability)를 보장하기 위한 락킹 프로토콜이다.



2PL의 필요성 

단순히 락을 사용한다고 해서 시리얼라이저빌리티가 보장되지 않는다.

락 사용에도 이상 현상이 발생할 수 있다.

2PL의 동작 방식 

확장 단계 (Growing Phase): 트랜잭션은 락을 계속 획득만 하고 해제하지 않는다.

축소 단계 (Shrinking Phase): 트랜잭션은 락을 해제만 하고 더 이상 새로운 락을 획득하지 않는다.

모든 락킹 오퍼레이션이 최초의 언락 오퍼레이션보다 먼저 수행되어야 한다.

2PL의 종류

Strict 2PL (S2PL) 

라이트 락을 트랜잭션이 커밋되거나 롤백될 때까지 유지한다.

롤백 시에도 이상 현상이 발생하지 않도록 리커버러빌리티를 보장한다.

Strong Strict 2PL (SS2PL) 

라이트 락뿐만 아니라 리드 락까지 커밋 또는 롤백 시까지 유지한다.

S2PL보다 구현이 쉽지만, 락을 더 오래 유지하여 성능에 영향을 줄 수 있다.

2PL의 문제점: 데드락 (Deadlock) 

두 트랜잭션이 서로 상대방이 가진 락을 기다리며 무한정 대기하는 상황이 발생할 수 있다.

데드락 해결 방식은 운영체제와 유사하다.



3.3. MVCC (Multi-Version Concurrency Control)
MVCC는 락 기반 방식의 성능 한계를 극복하기 위해 등장한 동시성 제어 기법이다.



MVCC의 등장 배경 

락 기반 방식은 리드-라이트, 라이트-리드 충돌 시 블록이 발생하여 처리량이 낮다.

리드와 라이트가 서로를 블록하지 않도록 해결하고자 했다.

MVCC의 기본 원리 

데이터 변경 시, 기존 데이터를 바로 수정하는 대신 새로운 버전을 생성한다.

각 트랜잭션은 자신의 트랜잭션 시작 시점 기준으로 커밋된 데이터를 읽는다.

이를 통해 읽기 작업이 쓰기 작업을 블록하지 않는다.

MVCC의 장단점 

장점: 동시 처리 가능한 트랜잭션 수가 증가하여 성능이 향상된다.

단점: 데이터 변경 이력을 관리하기 위해 추가적인 저장 공간이 필요하다.



4. MVCC와 격리 수준의 상호작용
MVCC는 각 격리 수준에서 어떻게 동작하며, 어떤 이상 현상을 방지하거나 허용하는지 살펴본다.



4.1. MVCC의 동작 방식 (Read Committed & Repeatable Read)
MVCC의 핵심 특징: 커밋된 데이터만 읽는다. 

Read Committed 레벨에서의 동작 

트랜잭션이 실행되는 시점에 커밋된 가장 최신 데이터를 읽는다.

예시: 트랜잭션 1이 x=10을 읽고, 트랜잭션 2가 x=50으로 변경 후 커밋하면, 트랜잭션 1이 다시 읽을 때 x=50을 읽는다.

Repeatable Read 레벨에서의 동작 

트랜잭션 시작 시점을 기준으로 그 전에 커밋된 데이터를 읽는다.

예시: 트랜잭션 1이 시작 시점(x=10)을 기준으로 데이터를 읽으므로, 트랜잭션 2가 x=50으로 변경 후 커밋해도 트랜잭션 1은 x=10을 읽는다.

RDBMS마다 기준 시점(트랜잭션 시작, 최초 리드 시점 등)이 다를 수 있다.



4.2. MySQL에서의 MVCC와 락킹 리드
로스트 업데이트 방지: SELECT ... FOR UPDATE (락킹 리드) 사용 

일반적인 SELECT는 MVCC에 따라 동작하지만, SELECT ... FOR UPDATE는 읽으면서 쓰기 락(Write Lock)을 획득한다.

이를 통해 다른 트랜잭션의 동시 쓰기를 막아 로스트 업데이트를 방지한다.

FOR UPDATE는 라이트 락을, FOR SHARE는 리드 락을 획득한다.

Repeatable Read 레벨에서의 라이트 스큐 해결: 락킹 리드 사용 

FOR UPDATE를 사용하여 읽기 시에도 락을 획득하면 라이트 스큐를 방지할 수 있다.

MySQL에서는 락킹 리드 시 가장 최근 커밋된 데이터를 읽는다.



4.3. PostgreSQL에서의 MVCC와 격리 수준
Read Committed 레벨: MVCC로 동작하며, MySQL과 유사하게 커밋된 데이터를 읽는다. 

Repeatable Read 레벨:

'First Committer Wins' 규칙 적용: 먼저 커밋한 트랜잭션이 승리하고, 나중에 커밋하려는 트랜잭션은 롤백된다. 

SELECT ... FOR UPDATE 사용 시, 이 규칙이 적용되어 실패할 수 있다.

Serializable 레벨:

SSI (Serializable Snapshot Isolation) 기법을 적용한 MVCC로 동작한다.

동작 방식은 'First Committer Wins'와 유사하다.

트랜잭션 간 아이솔레이션 레벨 차이: 서로 다른 아이솔레이션 레벨을 가진 트랜잭션이 상호작용할 때 예상치 못한 결과가 발생할 수 있다. 



4.4. MySQL의 Serializable 레벨
Repeatable Read 레벨과 유사하게 동작하지만, 내부적으로 일반 SELECT 문을 SELECT ... FOR SHARE처럼 암묵적으로 처리한다.

락 기반으로 동작하며, 성능을 위해 FOR SHARE를 사용하지만 데드락 발생 가능성이 높다.



4.5. PostgreSQL의 Serializable 레벨
SSI (Serializable Snapshot Isolation) 기법을 적용한 MVCC로 동작한다.

MVCC를 유지하면서 모든 이상 현상을 막는다.

'First Committer Wins' 방식으로 동작한다.



4.6. MVCC의 종합적 이해
MVCC는 오늘날 많은 RDBMS에서 성능 향상을 위해 사용된다.

구현 방식은 RDBMS마다 조금씩 다르므로, 사용 중인 DBMS의 문서를 숙지하는 것이 중요하다.

트랜잭션의 안정적인 운영을 위해 격리 수준과 MVCC 동작 방식을 이해하는 것이 필수적이다.
