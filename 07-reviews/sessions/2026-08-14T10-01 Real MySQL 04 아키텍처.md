## 추가로 확인한 사실

- Handler status는 handler 요청 횟수이며 physical disk I/O byte가 아니다.
- current `realmysql` 8.0.44는 BACKGROUND 35, FOREGROUND 4였고, foreground 중 `one_connection`은 2개였다.
- `thread_cache_size`는 종료된 connection thread 재사용 cache이며 실행 동시성을 제어하는 thread pool이 아니다.
- default `thread_handling`은 `one-thread-per-connection`; 공식 Enterprise Thread Pool은 별도 상용 plugin이다.
- InnoDB는 buffer pool miss read I/O와 dirty page background flush를 구분한다.

## 가장 중요한 보완 답변

- handler status는 storage engine row-operation 요청이지 SQL 수나 physical I/O가 아니다.
- processor affinity는 OS가 thread의 실행 가능 CPU를 제한하는 기능이며 group 수를 core 수에 맞추는 것만으로 hard pinning되지는 않는다.
- 모든 worker가 막히고 `thread_pool_max_threads`에 도달하면 새 worker를 더 만들지 못한다. statement는 기존 worker가 빌 때까지 queue에 남고 별도 timeout이 먼저 발생할 수 있다.
- active transaction statement를 high-priority로 끝내면 lock 보유 시간이 짧아져 전체 lock contention이 줄 수 있지만 low queue starvation도 관측해야 한다.

## 가장 중요한 보완 · recovery

- 정상 crash recovery의 `redo roll-forward → 미완료 transaction undo rollback`과 손상 시의 forced recovery를 분리했다.
- `innodb_force_recovery`는 repair 기능이 아니라 dump를 위한 emergency startup이다.
- redo 손상이라고 6부터 시작하지 않고, data directory·backup을 보존한 별도 copy에서 1부터 최소 단계로 올린다. 특히 4~6은 data file을 더 손상시킬 수 있는 위험 구간이다.
- 기동에 성공하면 application traffic을 붙이지 않고 data를 dump해 clean instance를 다시 구축한다. backup과 binary log PITR이 우선 복구 수단이다.

## 가장 중요한 보완 · buffer pool과 redo

- buffer pool의 page cache와 dirty page write buffering이라는 두 역할을 분리했다.
- 크기는 memory percentage 하나가 아니라 OS·global memory·connection별 local memory·peak task·OOM 여유의 예산으로 결정한다.
- online resize 단위는 `innodb_buffer_pool_chunk_size × innodb_buffer_pool_instances`이며 downsize는 page 회수를 동반해 특히 민감하다.
- free·LRU·flush list의 서로 다른 책임과 한 dirty page가 LRU·flush list에 동시에 속할 수 있음을 정리했다.
- midpoint insertion의 old 3/8과 `innodb_old_blocks_time`이 scan pollution을 줄이는 과정을 Mermaid로 시각화했다.
- WAL·clean/dirty page·LSN·checkpoint age를 연결하고, 너무 작은 redo capacity가 큰 buffer pool의 write buffering 효과를 제한할 수 있음을 정리했다.
- MySQL 8.0.30 이후 redo 용량은 `innodb_redo_log_capacity`, file은 `#innodb_redo` 구조로 관리됨을 책의 이전 설정과 구분했다.

## 핵심 정리 · flush와 warmup

- flush list flush는 오래된 dirty page를 기록해 checkpoint를 전진시키고 redo 공간을 재사용한다.
- LRU list flush는 LRU tail을 정리해 새 page를 받을 free frame을 확보한다.
- `innodb_io_capacity`는 device 최대 IOPS가 아니라 평상시 background I/O budget이고, `innodb_io_capacity_max`는 뒤처졌을 때의 burst 상한이다.
- adaptive flushing은 redo 생성률·checkpoint age를 보고 flush 속도를 조절한다. SSD는 보통 `innodb_flush_neighbors=0`을 유지한다.
- buffer pool dump는 page data가 아니라 page ID 목록이며, restart warmup 기능이지 data backup이 아니다.
- `INNODB_CACHED_INDEXES`의 cached page 수는 index 크기나 hit rate와 같지 않다.

## 핵심 정리 · Doublewrite

- redo는 변경 내용을 재실행하지만 torn page의 온전한 base page를 보장하지 않는다. Doublewrite가 완전한 page 사본을 제공하고 그 위에 redo를 적용한다.
- 책의 system tablespace 설명과 달리 MySQL 8.0.20부터는 별도 doublewrite file을 사용한다.
- Doublewrite·redo commit flush·binary log sync·backup은 서로 다른 failure를 다루므로 대체 관계가 아니다.

## 공식 자료와 version 차이

- 현재 MySQL 8.0의 buffer pool instance 기본은 환경에 따라 조건부다. non-Windows에서 buffer pool이 1GiB 이상이면 기본 8, 그보다 작으면 1이며 multiple instance는 1GiB 이상에서만 효과가 있다.
- 8.0.20+ Doublewrite는 별도 file, 8.0.30+는 `DETECT_ONLY`와 enabled mode 사이의 online 전환을 지원한다.
- 책의 숫자는 출발점으로만 보존하고 실제 설정은 설치 version의 공식 문서와 workload 지표로 판단한다.

## 핵심 연결 · undo lifecycle

```text
DML → undo 생성 → rollback 또는 MVCC version 재구성
COMMIT → 필요한 update undo는 history에 유지
oldest read view 종료 → purge 가능
purge → 내부 공간 재사용
truncate → 비워진 undo tablespace file의 물리 축소
```

- `COMMIT`과 undo 즉시 삭제를 분리하고, 장기 read-only RR transaction도 purge horizon을 붙잡을 수 있음을 정리했다.
- “100GB DELETE = 정확히 100GB undo”는 1:1 산식이 아니라 대량 DML이 큰 undo·redo·binary log를 만든다는 운영 경고로 보완했다.
- monitoring은 file size 단독이 아니라 oldest transaction age·History list length 추세·open read view·purge·disk·latency를 함께 보는 흐름으로 구성했다.
- undo tablespace → rollback segment → undo slot → undo log 계층과 16KiB page에서 segment당 1024 slots 계산을 시각화했다. 이 값은 실제 동시 transaction 처리량 보장값이 아니라 이론상 allocation 상한임을 명시했다.

## 시스템 변수와 version 차이

- `innodb_undo_tablespaces=2`는 8.0.14부터 deprecated·not configurable이므로 현재 표시값을 튜닝 대상으로 보지 않는다.
- 자동 물리 축소는 `innodb_undo_log_truncate`, `innodb_max_undo_log_size`, `innodb_purge_rseg_truncate_frequency`를 연결해 이해한다.
- `innodb_purge_threads`, `innodb_purge_batch_size`, `innodb_max_purge_lag*`는 원인인 장기 transaction을 해결한 뒤 검토할 고급 운영 변수로 분리했다.
- user-created undo tablespace는 `CREATE → INACTIVE → purge 후 EMPTY → DROP 또는 ACTIVE` 순서로 관리하며 기본 두 tablespace는 drop할 수 없다.
