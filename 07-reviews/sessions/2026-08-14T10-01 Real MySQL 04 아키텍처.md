## 추가로 확인한 사실

- Handler status는 handler 요청 횟수이며 physical disk I/O byte가 아니다.
- current `realmysql` 8.0.44는 BACKGROUND 35, FOREGROUND 4였고, foreground 중 `one_connection`은 2개였다.
- `thread_cache_size`는 종료된 connection thread 재사용 cache이며 실행 동시성을 제어하는 thread pool이 아니다.
- default `thread_handling`은 `one-thread-per-connection`; 공식 Enterprise Thread Pool은 별도 상용 plugin이다.
- InnoDB는 buffer pool miss read I/O와 dirty page background flush를 구분한다.

## 사용 환경과 공식 자료 확인

현재 `realmysql 8.0.44` container를 읽기 전용으로 확인했다.

```text
MySQL Community Server - GPL
thread_handling = one-thread-per-connection
thread_pool_* variables = 없음
```

따라서 지금까지 Docker 실습이 MySQL Enterprise였던 것은 아니다. AWS 공식 자료도 RDS for MySQL 8.0·8.4가 Community Edition을 지원한다고 밝힌다. Oracle MySQL Enterprise Thread Pool은 상용 plugin이고, Percona Server의 thread pool은 별도 호환 fork 구현이다.

현재 Percona Server 8.0 공식 문서 기준으로 `thread_pool_size`는 CPU core 수, `oversubscribe`는 3, `stall_limit`은 500ms, `max_threads`는 100000이 기본이다. 책과 설치 version 차이를 명시하고 운영에서는 설치 version 문서를 우선하도록 정리했다.

## 가장 중요한 보완 답변

- handler status는 storage engine row-operation 요청이지 SQL 수나 physical I/O가 아니다.
- processor affinity는 OS가 thread의 실행 가능 CPU를 제한하는 기능이며 group 수를 core 수에 맞추는 것만으로 hard pinning되지는 않는다.
- 모든 worker가 막히고 `thread_pool_max_threads`에 도달하면 새 worker를 더 만들지 못한다. statement는 기존 worker가 빌 때까지 queue에 남고 별도 timeout이 먼저 발생할 수 있다.
- active transaction statement를 high-priority로 끝내면 lock 보유 시간이 짧아져 전체 lock contention이 줄 수 있지만 low queue starvation도 관측해야 한다.

## 종합 영역 갱신 · 4.1.9

큰 지도·암기 카드·접힌 확인 질문·이어지는 내용·공식 확인 자료를 4.1.9까지의 전체 범위로 갱신했다. level은 2를 유지한다. 사용자가 architecture boundary와 thread pool 목적을 자기 말로 연결했지만, 실제 운영 지표를 보고 병목을 진단하는 level 3 답변은 아직 확인하지 않았다.

다음 시작점은 4.1.10 transaction-supported metadata다.

## 추가 캡처 · 4.1.10 트랜잭션 지원 메타데이터

- 새 원문은 [[4.1 MySQL 엔진 아키텍쳐#사용자 정리 원문]]에 그대로 append했다.
- MySQL 8.0 data dictionary와 별도 표기가 없는 system table이 InnoDB 기반 `mysql` system schema에 저장되는 구조를 정리했다.
- atomic DDL이 data dictionary update·storage engine operation·binary log write를 하나의 성공 또는 rollback으로 묶는다는 점을 연결했다.
- `Prepare → Perform → Commit → Post-DDL → crash recovery`를 Mermaid로 시각화하고 hidden `mysql.innodb_ddl_log`의 역할을 보완했다.
- atomic DDL과 transactional DDL·online DDL을 구분하고, non-InnoDB DDL과 plugin·component 설치 등 공식 예외를 기록했다.

## 종합 영역 갱신 · 4.1 완료

큰 지도·암기 카드·접힌 확인 질문·이어지는 내용·공식 확인 자료를 4.1.10까지 갱신했다. level은 2를 유지한다. “InnoDB metadata 저장 → transaction·DDL log → crash 후 roll forward 또는 rollback”의 인과는 설명했지만, 실제 DDL 장애·metadata lock 상황에서 지표를 선택한 사용자 답변은 아직 없다.

다음 시작점은 4.2 InnoDB storage engine architecture이며, 같은 `04-아키텍쳐/` 폴더에 새 canonical note를 만든다.

## 추가 캡처 · 4.2.1부터 4.2.3

- 새 canonical note [[4.2 InnoDB 스토리지 엔진 아키텍쳐]]를 만들고 사용자 원문을 표현·오타·URL까지 그대로 보존했다.
- 첨부한 트랜잭션 격리 수준·이상 현상·lock·MVCC 요약 380줄은 local reference로 원문 보존하고, 정리본에는 MySQL 8.0 InnoDB 내용만 다시 조직했다.
- `IMG_7571.JPG`는 InnoDB 전체 구조, `IMG_7572.jpg`~`IMG_7575.jpg`는 UPDATE 전·문장·commit 전 buffer pool과 undo·격리 수준별 SELECT 흐름에 배치했다.
- clustered index leaf의 전체 row, secondary index leaf의 PK와 double lookup을 Mermaid로 시각화했다.
- foreign key 검사가 parent·child index와 lock 범위를 넓혀 deadlock 가능성을 높이는 흐름을 추가했다.
- MVCC를 `read view → current version 또는 undo version`으로 정리하고, buffer pool과 undo log를 양자택일로 이해하지 않도록 바로잡았다.
- 쉬운코드 BJ.44·45·46-1·46-2를 isolation anomaly → lock·2PL → MVCC → `SELECT ... FOR UPDATE` 순서로 MySQL 관점에서 연결했다.
- lost update와 원문의 `write screw`(정확한 용어는 write skew)를 구분하고 atomic DML·optimistic locking·locking read의 선택 기준을 보완했다.

## 종합 영역 갱신 · 4.2.3

4.2 큰 지도·암기 카드·접힌 확인 질문·이어지는 내용·공식 확인 자료를 첫 세 절 기준으로 만들었다. level은 2를 유지한다. 사용자가 MVCC의 비차단 읽기 목적과 locking read 필요성을 연결했지만 실제 `INNODB_TRX`·`History list length`·`data_lock_waits`로 문제를 진단한 답변은 아직 확인하지 않았다.

다음 시작점은 4.2.4 잠금 없는 일관된 읽기(Non-Locking Consistent Read)다.

## 추가 캡처 · 4.2.4와 4.2.5

- 사용자 원문을 오타와 화살표 표현까지 [[4.2 InnoDB 스토리지 엔진 아키텍쳐#사용자 정리 원문]]에 그대로 append했다.
- `IMG_7576.JPG`를 변경 중인 row를 RU는 current version, RC·RR은 undo version으로 읽는 4.2.4 흐름에 배치하고 Mermaid로 재현했다.
- RU는 nonlocking이지만 dirty read가 가능해 엄밀한 consistent read는 아니라는 점을 보완했다.
- plain SELECT의 예외로 locking read, SERIALIZABLE, RR의 `INSERT ... SELECT`·`CREATE TABLE ... SELECT`, DML을 구분했다.
- long transaction이 old read view를 유지해 purge를 지연시키고 `History list length`를 키우는 흐름과 관측 SQL을 추가했다.
- wait-for graph의 cycle, 작은 transaction victim, rollback과 lock 해제를 Mermaid로 시각화했다.
- victim 크기는 공식 문서상 insert·update·delete row 수로 판단하며, 전용 detector thread의 주기적 검사라는 구현 표현은 동작 계약으로 외우지 않도록 보완했다.
- `innodb_table_locks`가 모든 MySQL lock을 감지하는 만능 설정이 아니며 `autocommit=0`·`LOCK TABLES` 문맥에 제한됨을 기록했다.
- detector OFF는 무한 대기가 아니라 `innodb_lock_wait_timeout`까지의 대기로 바뀌고, deadlock은 전체 transaction, timeout은 기본적으로 현재 statement만 rollback한다는 차이를 추가했다.
