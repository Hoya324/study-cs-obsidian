# 출석 보상 게임

## 문제와 제약

중복 요청과 동시 요청이 들어와도 사용자별 출석 보상 지급 상태가 꼬이지 않아야 하고, DB 밖의 외부 지급 결과까지 다뤄야 했다.

## 선택한 구조

- Kotlin·Spring Boot, PostgreSQL, Redis, Spring Cloud Gateway
- 업무 의도에서 UUIDv5 기반 결정적 idempotency key 생성
- `PENDING → 외부 지급 → COMPLETED` 상태 전이
- 사용자 단위 PostgreSQL advisory lock과 CAS 사용
- Redis 결과 저장소와 분산 lock 사용

## 보장한다고 말할 수 있는 범위

결정적 키와 상태 전이, 사용자 단위 직렬화로 동일 업무의 중복 실행을 줄이는 구조를 만들었다. 외부 지급 시스템과 로컬 DB가 하나의 원자 transaction이라는 뜻은 아니다.

## 실패 시나리오

- 외부 지급은 성공했지만 응답을 받기 전 timeout
- PENDING 기록 후 프로세스 종료
- lock lease·connection·Redis 장애
- 같은 사용자 요청과 다른 사용자의 전체 부하가 동시에 증가

## 관측과 복구

PENDING 체류 시간, idempotency hit, CAS 충돌, 외부 지급 timeout과 상태 불일치를 관측·대사해야 한다.

## 대안과 선택하지 않은 이유

DB constraint, row lock, outbox·보상, 외부 시스템 조회 API를 조합할 수 있다. 어떤 구조가 필요한지는 외부 지급의 idempotency·조회·취소 지원 여부에 달려 있다.

## 수치와 검증 방법

로컬 k6와 가짜 외부 지급 환경에서 약 700 TPS를 관찰했고 실제 지급 8,601건을 처리했다. 이 수치는 운영 한계가 아니며 test machine, latency, scenario와 외부 fake 조건을 함께 말해야 한다.

## 예상 면접 질문

- UUIDv5 key의 namespace와 입력은 무엇이며 충돌·수명 범위는?
- advisory lock과 CAS를 함께 사용한 각각의 책임은?
- 지급 성공 여부를 모르는 timeout을 어떻게 수렴시키는가?
