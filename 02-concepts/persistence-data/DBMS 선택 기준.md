# DBMS 선택 기준

## level 근거

아직 level 상승 근거 없음. [[01-1.2 왜 MySQL인가]]의 내용을 기록한 상태이며, 자기 말로 안정성의 구성 요소와 검증 방법을 설명해야 한다.

## 한 문장 정의

DBMS 선택은 데이터를 믿고 복구할 수 있는지를 먼저 확인한 뒤, 필요한 성능·기능과 운영 생태계를 비교하는 의사결정이다.

## 요청 흐름 속 위치

Spring 요청이 영속 데이터를 읽고 쓰는 경계인 [[DB 서버와 애플리케이션 서버]] 선택에 해당한다.

## 왜 필요한가

DBMS는 상태를 보관하므로 잘못된 선택은 단순 응답 지연을 넘어 데이터 손실, 정합성 훼손, 긴 복구와 마이그레이션으로 이어질 수 있다.

## 내부 동작

현재는 `안정성 → 성능과 기능 → 커뮤니티와 인지도`라는 평가 순서만 확보했다. 각 항목을 관찰 가능한 기준과 실제 부하 조건으로 세분화해야 한다.

## 소비하는 리소스

DBMS 자체는 CPU, 메모리, 디스크 I/O, 네트워크와 연결을 사용한다. 선택 과정에는 운영 인력, 학습 비용, 장애 대응 시간과 마이그레이션 비용도 포함된다.

## 실패 조건과 관찰되는 증상

- 장애 후 데이터가 복구되지 않거나 정합성이 깨진다.
- 필요한 처리량과 지연시간을 만족하지 못한다.
- 필요한 기능이나 운영 도구가 부족하다.
- 문서·사례·전문 인력이 부족해 장애 해결 시간이 길어진다.

## 측정 지표와 확인 방법

아직 답하지 못했다. 복구 목표, 데이터 손실 허용 범위, 장애 이력, 부하 테스트 결과, 기능 적합성, 지원 생태계를 어떤 증거로 확인할지 구체화한다.

## 해결 전략과 트레이드오프

인지도만으로 고르지 않고 서비스의 데이터 중요도와 실패 비용을 먼저 정의한다. 안정성이 충족된 후보 사이에서 성능·기능과 운영 비용을 비교한다.
