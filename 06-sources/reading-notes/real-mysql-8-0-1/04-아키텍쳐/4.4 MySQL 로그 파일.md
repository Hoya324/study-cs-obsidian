# 4.4 MySQL 로그 파일

## 한 문장

**에러 로그는 서버 생명주기·장애 원인, 제너럴 로그는 서버가 실제로 받은 요청, 슬로우 로그는 완료된 느린 요청을 조사한다. 아직 실행 중인 쿼리와 잠금 대기는 로그가 아니라 PROCESSLIST·Performance Schema·sys를 먼저 본다.**

~~~mermaid
flowchart TD
    A["무슨 문제가 생겼는가?"] --> B{"서버 시작·종료·장애?"}
    B -->|예| E["Error log"]
    B -->|아니오| C{"서버가 받은 SQL 전체가 필요한가?"}
    C -->|예| G["General log<br/>짧게 켜서 재현"]
    C -->|아니오| D{"이미 끝난 느린 SQL인가?"}
    D -->|예| S["Slow query log<br/>pt-query-digest로 집계"]
    D -->|아니오| L["현재 실행·대기 상태<br/>PROCESSLIST · Performance Schema · sys"]
    E --> X["OS·container·cloud log와 시간축 결합"]
    S --> P["EXPLAIN ANALYZE · index · lock · I/O 확인"]
~~~

## 사용자 정리 원문

> 언제 어떤 로그를 어떻게 봐야하는지 등을 보기좋게만 정리하면 될거같아. 이거까지하고 push

### 사진 표시 전사

사용자가 사진에 밑줄·별표·괄호로 표시한 내용을 의미를 바꾸지 않고 보존한다.

- 로그 파일을 이용하면 MySQL 서버의 깊은 내부 지식이 없어도 MySQL의 상태나 부하를 일으키는 원인을 쉽게 찾아서 해결할 수 있다.
- MySQL 서버에 문제가 생겼을 때는 로그 파일들을 자세히 확인하는 습관을 들일 필요가 있다.
- 에러 로그 파일의 위치는 설정 파일의 `log_error`에 정의된 경로로 확인한다.
- 슬로우 쿼리 로그는 쿼리가 정상적으로 완료된 뒤 실제 소요 시간을 기준으로 기록 여부를 판단한다.
- 슬로우 로그의 `Time`, `User@Host`, `Query_time`, `Lock_time`, `Rows_examined`, `Rows_sent`를 함께 해석한다.
- `Rows_examined`가 크고 `Rows_sent`가 작다면 더 적은 레코드에 접근하도록 튜닝할 가치가 있다.

## 증상별로 무엇을 먼저 볼까

| 증상·질문 | 1차 확인 | 왜 보는가 | 다음 행동 |
|---|---|---|---|
| 설정 변경 뒤 MySQL이 시작하지 않음 | **Error log** | 인식 못 한 변수·잘못된 값·권한·파일 경로 확인 | 첫 fatal/error부터 원인 수정 |
| MySQL이 갑자기 재시작·종료됨 | **Error log + OS/container log** | 정상 종료인지 crash·OOM·signal인지 구분 | 같은 시각의 kernel·Docker·cloud event 대조 |
| crash recovery가 실패함 | **Error log** | InnoDB recovery 진행·실패 지점 확인 | 백업 우선, 필요할 때만 `innodb_force_recovery` |
| `Aborted connection`, `Host ... is blocked` | **Error log** | client 종료·network·인증 실패 누적 확인 | 원인을 고친 뒤 `max_connect_errors` 재검토 |
| 서버가 실제로 어떤 SQL을 받았는지 필요 | **General log** | connect/disconnect와 수신한 statement 확인 | 짧은 재현 구간만 켜고 즉시 끔 |
| API가 느리고 이미 요청이 끝남 | **Slow query log** | 완료된 느린 SQL, 실행 횟수·누적 시간 확인 | `pt-query-digest` → 상위 fingerprint 분석 |
| 쿼리가 지금도 끝나지 않음 | **PROCESSLIST · Performance Schema · sys** | slow log는 완료 전 statement를 기록하지 않음 | wait·blocking transaction·stage 확인 |
| deadlock 원인 필요 | **SHOW ENGINE INNODB STATUS** + error log | 최근 deadlock과 잠금 관계 확인 | 필요 시 `innodb_print_all_deadlocks=ON`을 제한적으로 사용 |
| 데이터 변경 이력·복제·PITR | **Binary log** | 변경 event와 commit 순서가 목적 | `mysqlbinlog`, replica·backup 절차 사용 |

> [!important] 이름이 비슷해도 목적이 다르다
> **Redo log**는 crash recovery, **undo log**는 rollback·MVCC, **binary log**는 replication·PITR를 위한 내부/변경 로그다. 이번 절의 error·general·slow log는 주로 **운영 진단과 관측**에 사용한다.

### 4.4.1 에러 로그

### 언제 보는가

- 서버의 시작·종료와 설정 적용 여부
- 비정상 종료 뒤 InnoDB crash recovery
- query 처리 중 발생한 engine warning·error
- aborted connection, 인증·network·host block 문제
- deadlock·InnoDB monitor 출력

### 어디에 있고 어떻게 보는가

~~~sql
SHOW VARIABLES LIKE 'log_error';
SHOW VARIABLES LIKE 'log_error_services';
SHOW VARIABLES LIKE 'log_error_verbosity';
SHOW VARIABLES LIKE 'log_timestamps';
~~~

- 일반 설치는 `log_error`가 가리키는 파일 또는 시스템 로그를 본다.
- Docker처럼 `log_error=stderr`이면 container 표준 오류를 본다.

~~~bash
docker logs --since 30m realmysql
docker logs --tail 200 realmysql
~~~

### 읽는 순서

1. 장애 발생 시각과 timezone을 맞춘다.
2. 마지막 메시지가 아니라 **최초 원인 메시지**부터 찾는다.
3. 이어지는 recovery·shutdown 메시지는 원인의 결과인지 구분한다.
4. 같은 시각의 OS OOM, disk full, filesystem, container restart event를 대조한다.
5. 정상 종료라면 `Received SHUTDOWN from user` 같은 종료 요청을 찾고, stack trace·signal이면 crash를 의심한다.

~~~sql
SHOW ENGINE INNODB STATUS\G
SHOW VARIABLES LIKE 'innodb_print_all_deadlocks';
~~~

> [!warning] 운영 주의
> - InnoDB monitor나 모든 deadlock 출력을 계속 켜면 error log가 커질 수 있다.
> - `max_connect_errors`를 올리기 전에 network·client connection 종료 방식·인증 실패 원인을 먼저 찾는다.
> - OOM kill은 MySQL error log만으로 원인이 완성되지 않을 수 있으므로 OS/container log가 필요하다.

### 4.4.2 제너럴 쿼리 로그

### 언제 보는가

- client가 접속·종료했는지, 서버가 **실제로 어떤 statement를 받았는지** 재현할 때
- application이 기대와 다른 SQL을 보내는지 확인할 때
- 실행 전에 오류가 난 SQL까지 포함해 요청 순서를 추적할 때

제너럴 로그는 statement를 **받은 시점**에 기록하므로 실행 실패 SQL도 남을 수 있다. 반면 실행 시간·실행 계획·전체 잠금 상태를 분석하는 주 도구는 아니다.

~~~sql
SHOW VARIABLES
WHERE Variable_name IN ('general_log', 'general_log_file', 'log_output');

SET GLOBAL log_output = 'FILE';
SET GLOBAL general_log = ON;
-- 짧은 재현
SET GLOBAL general_log = OFF;
~~~

| `log_output` | 의미 | 주의 |
|---|---|---|
| `FILE` | 파일에 기록 | 운영에서 가장 단순하지만 rotation·disk 사용량 관리 필요 |
| `TABLE` | `mysql.general_log`에 기록 | SQL 조회는 쉽지만 table write overhead가 큼 |
| `FILE,TABLE` | 둘 다 기록 | 진단 비용도 둘 다 발생 |
| `NONE` | destination 없음 | 로그 enable 상태와 별개로 출력되지 않음 |

> [!warning] 항상 켜 두지 않는다
> 모든 statement를 기록하므로 I/O·용량·민감정보 노출 비용이 크다. 재현 범위와 시간을 먼저 정하고 켠 뒤 즉시 끈다. 현재 실행 중인 SQL은 `SHOW FULL PROCESSLIST`나 Performance Schema가 더 적합하다.

### 4.4.3 슬로우 쿼리 로그

### 언제 기록되는가

- statement가 **완료**되고 lock이 해제된 뒤 기록된다.
- 실행 시간이 `long_query_time`을 초과하고 `min_examined_row_limit` 조건을 만족해야 한다.
- 따라서 아직 실행 중인 3분짜리 query가 slow log에 없다고 해서 빠른 query가 아니다.

### 핵심 시스템 변수

| 변수 | 역할 | 운영 판단 |
|---|---|---|
| `slow_query_log` | slow log 활성화 | 진단·상시 관측 정책에 따라 사용 |
| `slow_query_log_file` | FILE destination 경로 | disk·rotation 확인 |
| `long_query_time` | slow 기준 시간(소수 초 가능) | 관측 목적과 트래픽에 맞게 조절 |
| `min_examined_row_limit` | 최소 examined rows | 사소한 query 폭증을 줄일 때 사용 |
| `log_queries_not_using_indexes` | index 미사용 query 추가 기록 | full scan이 정상인 작은 table도 포함되어 폭증 가능 |
| `log_throttle_queries_not_using_indexes` | index 미사용 로그 분당 제한 | 위 옵션의 log flood 완화 |
| `log_slow_admin_statements` | admin statement 포함 | DDL·관리 작업 점검 시 |
| `log_slow_extra` | FILE slow log에 추가 상태 정보 | 더 풍부한 원인 분석이 필요할 때 |
| `log_output` | `FILE`·`TABLE`·둘 다·`NONE` | TABLE은 편리하지만 부하 고려 |

~~~sql
SHOW VARIABLES
WHERE Variable_name IN (
  'slow_query_log',
  'slow_query_log_file',
  'long_query_time',
  'min_examined_row_limit',
  'log_queries_not_using_indexes',
  'log_throttle_queries_not_using_indexes',
  'log_slow_admin_statements',
  'log_slow_extra',
  'log_output'
);
~~~

### 아직 끝나지 않은 느린 쿼리

~~~sql
SHOW FULL PROCESSLIST;

SELECT THREAD_ID,
       EVENT_NAME,
       TIMER_WAIT / 1000000000000 AS elapsed_seconds,
       SQL_TEXT
FROM performance_schema.events_statements_current
WHERE SQL_TEXT IS NOT NULL;

SELECT *
FROM sys.innodb_lock_waits\G
~~~

### slow log 한 건 읽기

| 필드 | 의미 | 해석할 때 주의 |
|---|---|---|
| `Time` | 기록된 종료 시각 | 시작 시각은 대략 `Time - Query_time` |
| `User@Host` | 실행 계정·client host | 어느 application instance인지 연결 |
| `Query_time` | 전체 실행 시간 | 긴 query의 1차 기준 |
| `Lock_time` | MySQL server layer에서 계측한 lock 관련 시간 | InnoDB record lock 대기 전체를 완전하게 뜻하지 않음 |
| `Rows_examined` | 처리 과정에서 살펴본 row 수 | 크면 scan·index 선택·join 순서 점검 |
| `Rows_sent` | client에 보낸 결과 row 수 | examined/sent 격차가 크면 불필요 접근 가능성 |

집계 함수는 많은 row를 검사하고 적은 row를 반환하는 것이 정상일 수 있으므로 `Rows_examined / Rows_sent` 비율만으로 결론내리지 않는다.

## pt-query-digest로 많은 로그 요약

~~~bash
pt-query-digest /path/to/mysql-slow.log > slow-report.txt
pt-query-digest --type genlog /path/to/general.log > general-report.txt
pt-query-digest --order-by Query_time:max /path/to/mysql-slow.log
pt-query-digest --order-by Query_time:cnt /path/to/mysql-slow.log
~~~

`pt-query-digest`는 literal을 제거해 같은 형태의 SQL을 fingerprint(Query ID)로 묶는다.

#### 4.4.3.1 슬로우 쿼리 통계

| 보고서 영역 | 먼저 볼 것 |
|---|---|
| Overall | 기간·전체 query 수·unique fingerprint·QPS·동시성 |
| Profile | rank·누적 response time·호출 수·호출당 시간 |
| Query detail | min·max·avg·95%·median, rows examined/sent |
| Histogram | latency가 어느 구간에 몰렸는지 |
| Sample·EXPLAIN 정보 | 실제 구조·table·index 후보 |

#### 4.4.3.2 실행 빈도 및 누적 실행 시간순 랭킹

우선순위는 하나가 아니다.

- **누적 영향**: `Query_time:sum` — 서비스 시간을 가장 많이 소비한 query
- **최악 지연**: `Query_time:max` — timeout·tail latency 후보
- **실행 빈도**: `Query_time:cnt` — 한 번은 짧지만 너무 자주 실행되는 query
- **낭비 접근**: rows examined가 크고 rows sent가 작은 query

#### 4.4.3.3 쿼리별 실행 횟수 및 누적 실행 시간 상세 정보

~~~mermaid
flowchart LR
    A["증상 시간대 확정"] --> B["slow log 범위 추출"]
    B --> C["pt-query-digest 집계"]
    C --> D["sum · max · cnt 관점으로 후보 선정"]
    D --> E["원본 SQL·bind 값·schema 확인"]
    E --> F["EXPLAIN ANALYZE"]
    F --> G["index · query · lock · I/O 가설"]
    G --> H["대표 workload로 전후 측정"]
~~~

## 현재 실습 서버 `realmysql 8.0.44`

읽기 전용으로 확인한 현재 상태다.

~~~text
general_log                         = OFF
general_log_file                    = /var/lib/mysql/6dfb72e4014a.log
slow_query_log                      = OFF
slow_query_log_file                 = /var/lib/mysql/6dfb72e4014a-slow.log
long_query_time                     = 10.000000
min_examined_row_limit              = 0
log_queries_not_using_indexes       = OFF
log_slow_admin_statements           = OFF
log_slow_extra                      = OFF
log_output                          = FILE
log_error                           = stderr
log_error_services                  = log_filter_internal; log_sink_internal
log_error_verbosity                 = 2
log_timestamps                      = UTC
max_connect_errors                  = 100
innodb_print_all_deadlocks          = OFF
~~~

이 container의 error log는 파일이 아니라 `stderr`이므로 `docker logs realmysql`로 본다. general·slow log는 현재 OFF이며, 분석 도구 `pt-query-digest`도 local에 설치되어 있지 않다.

## 함정과 운영 원칙

1. **시간축을 먼저 맞춘다.** MySQL log timezone, application timezone, container·cloud timestamp가 다를 수 있다.
2. **`Lock_time`만으로 InnoDB lock을 단정하지 않는다.** live wait와 Performance Schema를 함께 본다.
3. **index 미사용 로그를 무작정 켜지 않는다.** 정상 full scan까지 대량 기록될 수 있다.
4. **TABLE destination이 공짜가 아니다.** 조회 편의와 write overhead를 교환한다.
5. **로그에는 개인정보·token·SQL literal이 들어갈 수 있다.** 접근 권한·보존·마스킹 정책이 필요하다.

## 암기 카드

- **서버가 아프다 → Error**
- **무엇을 받았나 → General**
- **무엇이 늦게 끝났나 → Slow**
- **아직 안 끝났다 → LIVE 조회**
- slow query 우선순위는 **총합(sum) · 최악(max) · 빈도(cnt)**

## 확인 질문

> [!question]- 설정 변경 뒤 MySQL이 시작하지 않을 때 가장 먼저 볼 것은?
> Error log다. 인식하지 못한 변수, 잘못된 값, 경로·권한 오류와 `ready for connections` 도달 여부를 확인한다.

> [!question]- 3분째 실행 중인 query가 slow log에 없는 이유는?
> slow log는 statement가 완료되고 lock이 해제된 뒤 기록되기 때문이다. 현재 query는 PROCESSLIST·Performance Schema·sys에서 본다.

> [!question]- General log와 Slow log의 기록 시점 차이는?
> General log는 서버가 statement를 받은 시점, Slow log는 실행을 정상적으로 마친 뒤 기준을 만족할 때 기록한다.

> [!question]- `Rows_examined`가 크고 `Rows_sent`가 작으면 무엇을 의심하는가?
> 불필요한 scan, 부적절한 index·join 순서·조건을 의심한다. 단 집계 query처럼 정상적인 경우도 있어 실행 계획과 함께 판단한다.

> [!question]- pt-query-digest의 fingerprint는 왜 필요한가?
> literal만 다른 같은 형태의 SQL을 하나의 Query ID로 묶어 횟수·누적 시간·분포를 비교하기 위해서다.

> [!question]- `Host ... is blocked`가 나오면 `max_connect_errors`만 올리면 되는가?
> 아니다. client의 비정상 종료, network, 인증 실패 원인을 먼저 찾고 필요할 때 제한값을 재조정한다.

> [!question]- Redo log와 Slow query log의 차이는?
> Redo는 crash recovery와 durability를 위한 InnoDB 내부 변경 기록이고, Slow log는 완료된 느린 statement를 운영자가 분석하기 위한 진단 로그다.
