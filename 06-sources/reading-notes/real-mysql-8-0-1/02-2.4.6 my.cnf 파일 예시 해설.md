# 02-2.4.6 my.cnf 파일 예시 해설

## 읽은 위치와 자료 상태

- 책: [[Real MySQL 8.0 1]]
- 범위: 02 설치와 설정 · 2.4.6 `my.cnf` 파일
- 입력: 46쪽부터 이어지는 사진 5장
- 판독 한계: 첫 사진의 오른쪽 일부와 다음 쪽 이후 내용은 촬영 범위 밖이다. 보이는 설정은 모두 아래에 분류했으며, 보이지 않는 행은 추측해 채우지 않았다.

## 이 예시를 읽는 핵심

이 파일은 “MySQL 8.0의 권장 기본값 모음”이 아니라 **특정 서버와 workload를 위한 하나의 운영 예시**다. 각 숫자를 복사하는 대신 다음 순서로 읽는다.

`목표 기능 → 사용하는 자원 → 실패했을 때 잃는 것 → 관찰 지표 → 서버 버전·장비·workload에 맞춘 값`

> [!tip] 먼저 볼 학습용 요약
> 103개를 모두 외우지 않는다. [[MySQL 외워둘 핵심 설정]]에서 우선순위를 잡고, 장애나 튜닝 때는 [[MySQL 상황별 설정 점검표]]에서 증상으로 역추적한다.

## 1. 서버 식별·경로·기본 엔진

| 사진의 option | 역할 | 적용 전 확인 |
|---|---|---|
| `server-id=1` | replication topology에서 server 식별 | 복제 참여 서버마다 고유해야 함 |
| `user=mysql` | `mysqld`를 실행할 OS user | MySQL 계정이 아님; directory 권한과 연결 |
| `datadir=/data/mysql/` | table·system data가 놓이는 기준 경로 | volume, 소유권, backup과 복구 경로 |
| `default_storage_engine=innodb` | 새 일반 table의 기본 engine | 8.0 기본도 InnoDB |
| `default_tmp_storage_engine=innodb` | 사용자가 만드는 `TEMPORARY TABLE`의 기본 engine | internal temporary table 설정과는 구분 |
| `socket=/tmp/mysql.sock` | local Unix socket path | 아래 `[client]`의 socket과 일치시킴 |
| `default-time-zone='+09:00'` | server global time zone 초기값 | application/JDBC·UTC 저장 정책과 함께 결정 |

## 2. table·file·packet·connection 한도

| 사진의 option | 역할 | 비용과 위험 |
|---|---|---|
| `table_open_cache=30000` | 열어 둔 table descriptor cache | memory와 file descriptor 사용 증가 |
| `table_open_cache_instances=16` | table cache를 분할해 contention 완화 | cache instance별 관리 비용 |
| `open-files-limit=65535` | `mysqld`의 open file 한도 목표 | OS `ulimit`가 더 낮으면 원하는 값이 안 나올 수 있음 |
| `max_allowed_packet=67108864` | client/server packet 최대 크기 64 MiB | 큰 BLOB·bulk query 허용과 connection memory 영향 |
| `max_connections=8000` | 동시 client connection 상한 | 숫자만 올리면 thread stack·session buffer·scheduler·FD 고갈 가능 |
| `max_connect_errors=999999` | host 차단 전 연속 실패 허용치 | 장애 완화에는 편하지만 공격·오설정 탐지 약화 가능 |

Spring의 HikariCP 관점에서는 `모든 application instance의 maximumPoolSize 합 + batch·관리·replica connection`이 DB의 connection budget 안에 들어와야 한다. `max_connections=8000`을 application pool 크기로 그대로 해석하지 않는다.

## 3. SQL 의미·문자셋·접속 보안

| 사진의 option | 역할 | 주의 |
|---|---|---|
| `explicit_defaults_for_timestamp=ON` | `TIMESTAMP`의 암묵적 초기화 동작 제거 | 8.0에서는 기본 동작과 가까움 |
| `sql-mode=STRICT_TRANS_TABLES,...` | 잘못된 날짜·0 나눗셈·engine 대체 처리 규칙 | application validation과 SQL 호환성에 직접 영향 |
| `character-set-server=utf8mb4` | server default charset | schema/table/column의 기존 charset을 자동 변경하지 않음 |
| `character-set-filesystem=utf8mb4` | file name literal 해석 charset | 일반 data charset 설정이 아님 |
| `collation_server=utf8mb4_0900_ai_ci` | server default collation | `ai_ci`는 accent·case insensitive 의미 |
| `skip-character-set-client-handshake` | client가 요청한 charset을 무시하고 server 설정 강제 | JDBC connection charset과 불일치 가능; 신중히 사용 |
| `skip-name-resolve` | account host matching에 DNS 이름을 사용하지 않음 | hostname 기반 account 대신 IP·pattern 필요 |
| `local_infile=OFF` | client local file을 server로 읽는 기능 제한 | data import 편의와 공격 표면의 교환 |
| `secure-file-priv=/data/securefile/` | server-side import/export directory 제한 | directory 권한과 함께 관리 |
| `block_encryption_mode='aes-256-ecb'` | `AES_ENCRYPT/DECRYPT` 기본 block mode | TDE 설정이 아니며 ECB는 pattern 노출 특성이 있어 용도별 암호 설계 필요 |

## 4. 계정·역할·비밀번호

| 사진의 option | 역할 | 주의 |
|---|---|---|
| `activate_all_roles_on_login=1` | login 시 부여된 role을 기본 활성화 | 최소 권한 정책과 함께 검토 |
| `default_password_lifetime=0` | 기본 password 만료를 사용하지 않음 | 조직의 계정 정책에 따라 결정 |
| `password_history=5` | 최근 password 재사용 제한 | account별 override 가능 |
| `validate_password.length=8` | 최소 비밀번호 길이 | component/plugin 설치 여부부터 확인 |
| `validate_password.mixed_case_count=2`, `number_count=2`, `special_char_count=2` | 대소문자·숫자·특수문자의 최소 개수 | 길이 8과 함께 쓰면 실제 조합 가능성도 확인 |
| `validate_password.dictionary_file=prohibitive_dictionary.data` | 금지할 단어 사전 | 파일 경로와 읽기 권한 확인 |
| `validate_password.policy=STRONG` | 강한 validation policy | 자동화 계정 rotation 방식과 함께 설계 |

## 5. 임시 table·full-text·기타 동작

| 사진의 option | 역할 | 비용과 관찰 |
|---|---|---|
| `max_heap_table_size=10M` | user-created `MEMORY` table 상한 등에 관여 | `tmp_table_size`와 동일 개념이 아님 |
| `tmp_table_size=10M` | internal in-memory temporary table 한도에 관여 | 초과 시 disk temporary table 증가 가능 |
| `tmpdir=/data/mytmp/` | temporary file 경로 | 여유 공간·I/O latency·권한 관찰 |
| `ngram_token_size=2` | ngram full-text parser token 크기 | index 재생성과 검색 품질·크기 영향 |
| `sysdate-is-now` | `SYSDATE()`를 `NOW()`처럼 statement 시작 시각으로 동작 | replication 결정성과 연결 |
| `core-file`, `innodb_buffer_pool_in_core_file=OFF` | crash core dump를 만들되 buffer pool page는 제외 | dump 크기와 민감 data 노출 감소, debugging 정보 감소 |

## 6. InnoDB 저장 경로와 tablespace

| 사진의 option | 역할 | 적용 전 확인 |
|---|---|---|
| `innodb_data_home_dir=/data/mysql/` | InnoDB system tablespace 경로 기준 | 초기화·이동 절차 필요 |
| `innodb_data_file_path=ibdata1:100M:autoextend` | system tablespace file과 증가 방식 | 운영 중 단순 경로 변경 금지 |
| `innodb_temp_data_file_path=ibtmp1:12M:autoextend` | global temporary tablespace file | temp 폭증과 disk 공간 관찰 |
| `innodb_file_per_table=ON` | table별 file-per-table tablespace 기본 | 개별 table 공간 회수·이동에 유리 |
| `innodb_undo_directory=/log/innodb-undo/` | 기본 undo tablespace 경로 | transaction rollback·MVCC와 연결, SSD 후보 |
| `innodb_rollback_segments=64` | undo tablespace별 rollback segment 수 | concurrency 특성에 맞춰 측정 |
| `innodb_undo_tablespaces=2` | 예시 당시 undo tablespace 수 | 8.0.14부터 설정 불가; 기본 2개와 SQL 관리 방식 사용 |
| `innodb_max_undo_log_size=536870912` | 자동 truncate 대상이 되는 undo tablespace 크기 기준 | long transaction과 purge 지연 관찰 |
| `innodb_undo_log_truncate=ON` | 커진 undo tablespace 자동 축소 | purge 작업 비용과 디스크 사용의 교환 |

## 7. redo·buffer pool·I/O와 내구성

| 사진의 option | 역할 | 핵심 trade-off |
|---|---|---|
| `innodb_log_group_home_dir=/log/innodb-log` | redo log directory | 별도 storage 사용 시 I/O 경합 완화 가능 |
| `innodb_log_files_in_group=3` + `innodb_log_file_size=2048M` | 과거 방식의 총 redo 공간 약 6 GiB | 8.0.30부터 `innodb_redo_log_capacity`가 대체 |
| `innodb_buffer_pool_size=20G` | InnoDB data·index page shared cache | host RAM과 다른 process·connection memory를 뺀 뒤 결정 |
| `innodb_buffer_pool_instances=10` | buffer pool 분할 | 8.0.44에는 있으나 값은 pool 크기·contention에 맞춤 |
| `innodb_sort_buffer_size=64M` | InnoDB index 생성용 sort buffer | connection별 일반 `sort_buffer_size`와 다름 |
| `innodb_adaptive_hash_index=OFF` | adaptive hash index 비활성화 | point lookup 이점과 contention을 workload로 비교 |
| `innodb_doublewrite=OFF` | torn page 보호 비활성화 | atomic write가 보장되지 않으면 corruption 복구 능력 저하 |
| `innodb_checksum_algorithm=CRC32` | page checksum | corruption 탐지 비용과 보호 |
| `innodb_flush_log_at_trx_commit=0` | commit마다 redo를 disk에 동기화하지 않음 | 처리량 대신 crash 시 최근 commit 유실 가능 |
| `innodb_flush_method=O_DIRECT_NO_FSYNC` | data file direct I/O, 일부 `fsync` 생략 | filesystem·hardware의 ordering/durability 보장을 확인해야 함 |
| `innodb_io_capacity=1000`, `innodb_io_capacity_max=5000` | background flushing IOPS 가이드 | storage 실제 IOPS와 dirty page 추세로 보정 |
| `innodb_ft_enable_stopword=OFF` | InnoDB full-text stopword 사용 중지 | index 크기·검색 결과·재색인 필요성 영향 |

사진의 `innodb_flush_log_at_trx_commit=0`, `sync_binlog=0`, `innodb_doublewrite=OFF` 조합은 하나씩 따로 볼 설정이 아니다. **commit 유실, binlog와 InnoDB 상태 불일치, torn page 복구**라는 서로 다른 내구성 방어선을 동시에 약하게 만든다.

## 8. 장애·lock 관측과 Performance Schema

| 사진의 option | 역할 | 비용과 주의 |
|---|---|---|
| `innodb_status_output_locks=ON` | InnoDB status에 lock 정보 추가 | `innodb_status_output`과 함께 동작 여부 확인 |
| `innodb_print_all_deadlocks=ON` | 모든 deadlock을 error log에 기록 | 진단력 증가, log volume 증가 |
| `innodb_cmp_per_index_enabled=ON` | compressed table index별 통계 | memory·CPU 계측 비용 |
| `performance_schema=ON` | server 내부 event 계측 기반 | startup 설정 |
| `stage/%`, `memory/%`, `wait/%` instruments 모두 `ON` | stage·memory·wait 계측 활성화 | 필요한 instrument만 켜 overhead 제한 |
| stage current/history/history_long 모두 `ON` | 실행 stage의 현재·짧은·긴 이력 저장 | 긴 이력은 server 전체 memory 사용 |
| statement history `OFF`, history_long `ON` | thread별 짧은 SQL 이력은 끄고 전체 긴 이력은 저장 | 목적이 명확한지 확인 |
| wait current/history/history_long 모두 `ON` | 현재와 과거 wait event 저장 | 병목 분석 범위와 overhead 교환 |
| stage·statement·wait history size `10` | thread별 짧은 이력 row 수 | 관측 window가 매우 짧음 |
| stage·statement·wait history-long size `50000` | instance 전체 긴 이력 row 수 | 책 예시는 현재 실습값 10,000보다 5배 큼 |

Performance Schema는 “로그 파일”이 아니라 instance 안의 in-memory 관측 계층이다. `instrument → consumer → event table → sys schema/query` 흐름으로 읽는다.

## 9. TDE

| 사진의 option | 역할 | 현재 버전 주의 |
|---|---|---|
| `early-plugin-load=keyring_file.so` | server 초기 단계에 keyring plugin 적재 | `keyring_file` plugin은 8.0.34부터 deprecated |
| `keyring_file_data=/data/tde/tde_master.key` | keyring file 위치 | DB data와 key를 같은 backup·권한 경계에 두지 않음 |

이 설정은 keyring을 준비하는 단계다. 실제 tablespace encryption 여부는 별도 설정과 DDL을 확인해야 한다. 최신 배포에서는 `component_keyring_file` 등 component 기반 keyring을 우선 검토한다.

## 10. binary log와 복제

| 사진의 option | 역할 | 비용과 주의 |
|---|---|---|
| `log-bin=/log/mysql-bin/mysql-bin` | binlog 활성화와 basename | replication·CDC·PITR의 입력, disk·보존 비용 |
| `sync_binlog=0` | OS가 binlog flush 시점 결정 | 성능 대신 OS/power crash 시 binlog 유실 위험 |
| `gtid-mode=ON`, `enforce_gtid_consistency=ON` | GTID 기반 transaction 식별과 안전한 SQL 제약 | failover·topology 변경을 단순화 |
| `binlog_checksum=CRC32` | binlog event checksum | 전송·보관 중 손상 탐지 |
| `binlog_order_commits=ON` | storage engine commit 순서와 binlog 순서를 맞춤 | replica consistency와 병렬 commit 성능에 연결 |
| `binlog_format=ROW` | row event 기록 | 정확한 복제·CDC에 유리, volume 증가 가능 |
| `binlog_row_image=MINIMAL` | 변경에 필요한 최소 row image 기록 | volume 감소, 일부 CDC·flashback 도구 요구사항 확인 |
| `binlog_rows_query_log_events=ON` | row event에 원 SQL 관련 정보 추가 | 진단성 증가와 binlog 증가 |
| `max_binlog_size=104857600` | binlog file rotation 기준 약 100 MiB | 큰 transaction 하나는 기준을 넘을 수 있음 |
| `binlog_expire_logs_seconds=259200` | 3일 뒤 자동 만료 | 복구 목표·replica 지연보다 짧으면 필요한 log 소실 |
| `log_slave_updates` | replica가 적용한 변경도 자신의 binlog에 기록 | chain replication·promotion에 필요; 최신 이름은 `log_replica_updates` |

## 11. replica와 relay log

| 사진의 option | 역할 | 현재 이름·주의 |
|---|---|---|
| `slave_parallel_type=LOGICAL_CLOCK` | 병렬 적용 scheduling 방식 | 8.0.26 이후 `replica_parallel_type`; 8.0.29부터 변수 자체도 deprecated 방향 |
| `slave_parallel_workers=4` | replica applier worker 수 | 최신 이름 `replica_parallel_workers`; 많다고 항상 빠르지 않고 lock contention 가능 |
| `slave_preserve_commit_order=1` | source의 commit 순서 보존 | 최신 이름 `replica_preserve_commit_order` |
| `relay-log=/log/relay-bin/relay-bin` | relay log basename | hostname 변경·복구를 고려한 명시적 경로 |
| `relay_log_info_repository=TABLE` | applier metadata를 table에 저장 | 8.0 기본이 TABLE이며 변수는 8.0.23부터 deprecated이므로 생략 권장 |
| `relay_log_recovery=ON` | crash 뒤 relay log 복구 | crash-safe replica 운용과 연결 |
| `relay_log_purge=ON` | 적용 완료 relay log 자동 제거 | disk 절약, 보존 목적이 있으면 정책 검토 |

## 12. error·slow log·시간과 보존

| 사진의 option | 역할 | 비용과 주의 |
|---|---|---|
| `log-error=/log/mysql-err.log` | error log 위치 | volume mount·rotation·권한 필요 |
| `log_error_verbosity=1` | ERROR만 기록 | replication·connection 진단 정보가 부족할 수 있어 공식 문서는 복제 시 2 이상 권장 |
| `slow-query-log=1` | slow log 활성화 | I/O와 민감 SQL 관리 필요 |
| `long_query_time=1` | 1초 이상 query 후보 | latency SLO와 workload에 맞춰 결정 |
| `log_slow_extra=1` | scanned row·temp table·sort 등 추가 지표 | 원인 분석력과 log 크기 증가 |
| `log_slow_admin_statements=1` | 느린 admin statement 포함 | 운영 작업 분석에 유용 |
| `log_slow_slave_statements=1` | replica statement 포함 | 8.0.26 이후 `log_slow_replica_statements`; ROW 복제에는 효과 제한 |
| `slow_query_log_file=/log/mysql-slow.log` | slow log 파일 | rotation·disk full alert 필요 |
| `log-raw` | 수신 SQL 원문 logging | password rewriting을 우회할 수 있어 production 비권장 |
| `log_timestamps=SYSTEM` | file log timestamp에 system time 사용 | 여러 서버의 상관 분석에는 UTC가 단순할 수 있음 |

## 현재 8.0에서 특히 고쳐 읽을 항목

| 사진 표기 | 8.0 후반에서의 해석 |
|---|---|
| `innodb_log_files_in_group`, `innodb_log_file_size` | 8.0.30부터 deprecated, `innodb_redo_log_capacity` 사용 |
| `innodb_undo_tablespaces=2` | 8.0.14부터 설정 불가; 기본 2개와 `CREATE UNDO TABLESPACE` 사용 |
| `early-plugin-load=keyring_file.so` | 8.0.34부터 plugin deprecated, component keyring 검토 |
| `slave_*`, `log_slave_updates`, `log_slow_slave_statements` | 8.0.26부터 `replica_*` 명칭 우선 |
| `relay_log_info_repository=TABLE` | 기본이 TABLE이며 변수 자체가 8.0.23부터 deprecated, 생략 |

## 현재 실습 instance와 차이

[[Real MySQL 예시와 realmysql 8.0.44 설정 비교]]에서 사진 예시를 실제 Docker `realmysql` 8.0.44의 runtime 값과 대조했다. 예시는 20 GiB buffer pool·8000 connections·별도 `/data`, `/log` mount를 전제로 하지만 현재 실습 instance는 128 MiB buffer pool·151 connections와 container 기본 경로를 사용한다.
